# Спецификация реализованной части системы «Цифровой двойник»

## 0. Краткая сводка

**Что есть.** Рабочий прототип: любой пользователь в личном чате Telegram/VK может после согласия заполнить анкету из четырёх блоков; после заполнения профиль создаётся автоматически. До создания профиля пользователь может по желанию добавить переписку из TXT. После активации профиль доступен для диалога через локальную модель Ollama. Доступность `A_eff` управляет состоянием, лимитом генерации и задержкой ответа; тестовый цикл завершается блокировкой через 7 суток.

**Чего нет относительно ТЗ.** Клинически проверенного фильтра безопасности, NLP-агрегации `W/Osc`, планировщика недельных контрольных точек (`HOLD/NORMAL/SKIP`), соответствия очереди и задержки нормативным формулам ТЗ, шифрования, ролей и динамической системы приглашений, экспорта архива, маршрута импорта для психолога с линтером и версионированием, MAX-адаптера, полного Docker-окружения (в compose только БД), интеграционных тестов с реальными PostgreSQL/мессенджерами. Встроенная обработка кризисных сигналов — экспериментальная эвристика, не клинический скрининг. Тестовая доступность управляет состоянием, лимитом генерации и отложенной доставкой.

Перед четырьмя блоками анкеты задаётся обязательный вопрос об имени или псевдониме; настоящее имя указывать необязательно. Загрузка переписки из TXT предлагается только после анкеты и является необязательной; её содержимое после загрузки сохраняется в открытом виде и используется как воспоминания. Не загружайте переписку без права на передачу содержащихся в ней данных. Этот прототип не предназначен для реальных клиентских данных до внедрения шифрования и клинически/юридически проверенного согласия и оценки кризисной обработки специалистом.

**Критичное (P0), что нужно решить первым:**

| № | Суть | Раздел |
|---|---|---|
| DEF-01 | Системный промт предписывает двойнику выдавать себя за живого человека и не раскрывать свою природу. Это противоречит ТЗ, статье и этическим ограничениям работы | 10, TBD-01 |
| DEF-02 | Регистрация в Telegram/VK открыта всем; HTTP-метод `/chat` не защищён и нет привязки клиента к психологу | 10, TBD-02 |
| DEF-03 | Нет клинически валидированной кризисной оценки и пост-проверки ответов | 10, TBD-03, TBD-04 |

**Оценка готовности относительно ТЗ (ориентировочно).** Ядро диалога и канал VK — около трети объёма MVP; механизм угасания, безопасность, данные и администрирование — в основном впереди (раздел 9).

## 1. Назначение и границы реализованной части

### 1.1. Реализовано

1. Хранение профиля двойника, атрибутов стиля, ценностей, воспоминаний с векторными представлениями и истории диалога в PostgreSQL (с расширением pgvector).
2. Поиск до трёх воспоминаний по cosine similarity с настраиваемым порогом и фильтрацией несовместимых моделей эмбеддингов.
3. Вызов локальной модели через Ollama и сохранение диалога.
4. Вычисление состояния двойника по времени и активности; блокировка по сроку.
5. Четыре точки входа: консоль, REST (`POST /chat`), VK-бот (Long Poll), Telegram-бот (long polling); VK и Telegram используют общий движок анкеты.

### 1.2. Не входит в текущую версию

Всё перечисленное в разделе 9 со статусом **[НЕТ]**. Это не ошибки реализации, а следующие этапы по ТЗ.

## 3. Архитектура как реализовано

```mermaid
flowchart TD
    K[Консоль chat_console.py] --> C
    A[REST API main.py: POST /chat] --> C
    V[VK-адаптер vk_adapter.py] --> C
    T[Telegram-адаптер tg_adapter.py] --> C
    C[chat_service.chat] --> S[decay.compute_state]
    C --> R[retrieve: эмбеддинг запроса]
    C --> P[prompt_builder.build_system_prompt]
    R --> O[(Ollama: qwen3-embedding)]
    C --> M[(Ollama: qwen3:8b)]
    S --> DB[(PostgreSQL + pgvector)]
    R --> DB
    P --> DB
    C --> DB
```

Особенности текущей архитектуры:
- Все каналы вызывают одну функцию `chat(user_msg, twin_id, user_id)`
- Генерация синхронная; ответ возвращается в том же вызове (очереди доставки нет; TBD-08).
- Отдельных процессов-воркеров нет; планировщика (cron/worker) нет (TBD-07).
- В Docker работает только БД; приложение запускается на хосте.

### 4.1. Последовательность обработки сообщения (`chat()`)

1. `compute_state(twin_id)` → текущее состояние.
2. Обновление `TwinProfile.current_state` (если изменилось) и `last_interaction_at = now`.
3. Если состояние `LOCKED` → возврат пустой строки **без вызова модели**.
4. Загрузка до 20 последних сообщений для пары `(twin_id, user_id)`; они используются и для поиска, и для анализа временного контекста безопасности.
5. Локальные правила выделяют явные текущие намерения/непосредственную опасность и отдельно неоднозначные фразы. Эмбеддинги используются только для приблизительной LO/RO-ориентации, не для определения кризиса.
6. `should_search_memory()` пропускает простые приветствия и передаёт содержательные вопросы о профиле/прошлом в поиск; уточняющая реплика может быть переформулирована локальной Ollama с ограниченной историей.
7. Если одобренный исходный TXT сохранён и помещается в общий бюджет контекста, передаётся полный текст как недоверенные данные; иначе используется существующий RAG с порогом `MEMORY_RELEVANCE_THRESHOLD`. Примеры стиля передаются отдельно от фактов.
8. `build_system_prompt(twin_id, state)` получает анкету, примеры речевой манеры и инструкции для состояния/уровня безопасности.
9. Ollama получает `OLLAMA_NUM_CTX` (по умолчанию 8192), настраиваемые параметры генерации и контекст в пределах оценочного бюджета; текущая реплика и обязательные системные инструкции сохраняются при сокращении.
10. Сохранение пары сообщений (`user`, `assistant`) в `chat_messages` и возврат ответа. Фиксированный кризисный ответ используется только для явных текущих сигналов `current`/`imminent`, а не по накопленному счёту.

TXT сохраняется как материал с неизвестным автором и датой; явные подписи остаются частью текста и не сопоставляются автоматически с человеком или цифровым образом. Старое значение `subject_material` трактуется в контексте как `unknown`, без изменения существующих записей. Обработка сохраняет абзацы, объединяет их в ограниченные по размеру фрагменты и по возможности делит длинный текст по предложениям. Это запасной разбор, а не поддержка произвольных экспортных форматов. Примеры речевой манеры отбираются эвристически; форматные подписи, цитаты и часть пересказов исключаются, но авторство оставшихся примеров не доказано.

Не выполняются: анализ состояния клиента (NLP), проверки ответа, расчёт задержки, шифрование, журнал решений.

### 5.6. `chat_messages` — история диалога

| Поле | Тип | Назначение |
|---|---|---|
| `id`, `twin_id` (FK, CASCADE) | Integer | |
| `user_id` | Text, not null | Идентификатор пользователя в мессенджере (VK / Telegram / MAX) |
| `role` | Text | `user` / `assistant` |
| `content` | Text | **Открытый текст, без шифрования** (DEF-09) |
| `grief_orientation` | Text, nullable | Приближённая классификация пользовательского сообщения: `LO` / `RO`; не диагноз |
| `crisis_signal` | Boolean, nullable | Локальное правило обнаружило явный текущий сигнал; `NULL`, если правило недоступно |
| `crisis_score` | Integer | Ограниченный экспериментальный счёт для пары профиля и пользователя |
| `crisis_escalated` | Boolean | На сообщении обнаружен явный текущий сигнал, вызвавший кризисный ответ |
| `created_at` | DateTime(tz), server default `now()` | |

Кризисный уровень (`none`, `ambiguous`, `current`, `imminent`) определяется локальными языковыми правилами и ограниченными маркерами времени/контекста. Рассказ о прошлом, утрате или смерти сам по себе не приводит к экстренному ответу. Неоднозначная фраза просит кратко уточнить текущую безопасность; явное текущее намерение или непосредственная опасность обходят порог накопления и сразу запускают кризисный ответ. LO/RO-ориентация остаётся приблизительной и использует локальные эмбеддинги только между двумя ориентационными эталонами. Если эмбеддинги недоступны, LO/RO остаётся неопределённым, а правила безопасности продолжают работать; при исключительной ошибке правил сохраняется `NULL`, без утверждения о достоверно безопасном сообщении.

`crisis_score` увеличивается на 1 для неоднозначного сигнала, на 2 для текущего/непосредственного сигнала (максимум 3) и постепенно уменьшается на обычных сообщениях. Сам счёт не вызывает экстренный ответ. Предыдущее значение загружается только для пары `(twin_id, user_id)`, поэтому не переносится между профилями или пользователями. Это детерминированная эвристика, а не клинически надёжный классификатор; нужны проверка специалистом, расширенная разметка и анализ ложных срабатываний и пропусков. Синтетические сценарии находятся в `tests/data/crisis_scenarios.json`.

### 5.6.1. `outbox` — отложенные ответы

Хранит канал и адресата, текст ответа, время доставки, статус, число попыток, время захвата воркером, время успешной отправки, тип последней ошибки и ID Telegram-сообщения-заглушки. Ответ и запись outbox создаются в одной транзакции. Воркеры Telegram и VK выбирают готовые записи через `FOR UPDATE SKIP LOCKED`; зависшие `sending` повторно захватываются после тайм-аута. После 8 ошибок сообщение получает статус `failed`, текст сохраняется для диагностики.

Доставка имеет семантику **at least once**: если отправка прошла, но процесс завершился до отметки `sent`, при повторе возможно дублирование. Очередь не гарантирует exactly-once для внешних API.

### 5.6.2. Таблицы из ТЗ, которых нет

`schedule_state` (с режимом недели и подписью), `state_event` (хэш-цепочка), `nlp_result`, `daily_aggregate`, `filter_event`, `gen_trace`, `consent`, `audit_log`, `corpus_chunk` с метаданными. → TBD-07, TBD-09, TBD-04, TBD-11, TBD-05.

Явных индексов нет: ни векторного (HNSW/IVFFlat), ни по `(twin_id, user_id, created_at)` в `chat_messages`.

## 6. Функциональная спецификация модулей

### 6.1. `db/connection.py`

- Формирует `DATABASE_URL = postgresql://USER:PASSWORD@HOST:PORT/NAME` из переменных окружения.
- Создаёт `engine` с `pool_pre_ping=True` и фабрику `SessionLocal`.
- **Ограничения:** при отсутствии обязательной переменной — `KeyError`; конфигурация загружается при импорте; пароль в `.env` (секреты Docker не используются; TBD-11).

### 6.2. `scripts/init_db.py`

- Добавляет корень проекта в `sys.path`, вызывает `Base.metadata.create_all(engine)`, печатает «Таблицы созданы».
- **Не создаёт расширение `vector`.** Если оно не создано скриптами в `docker-entrypoint-initdb.d`, создание таблицы `twin_memories` завершится ошибкой (DEF-13).

### 6.3. `scripts/load_character.py`

- Создаёт двойника «Алексей» в состоянии `ACTIVE`, `activated_at = now`.
- Добавляет два атрибута стиля (`speech_length`, `humor_type`), две ценности, одно «презираемое» качество и одно воспоминание (эмбеддинг через `ollama.embeddings`).
- **Ограничения:** комментарий «остальные атрибуты» — заглушка; при каждом запуске создаётся **новый** двойник (скрипт не идемпотентен); корпус из одного воспоминания непригоден для проверки RAG; нет импорта из JSON/TXT, разметки тем, анкеты в полном объёме (TBD-13).

### 6.4. `services/core/chat_service.py`

#### `retrieve(query, twin_id, k=3) -> RetrievalResult`
- Строит эмбеддинг запроса моделью `EMBED_MODEL` (`qwen3-embedding:0.6b` по умолчанию), выбирает `k` ближайших воспоминаний и возвращает фрагмент, similarity и доступные метаданные только для записей той же модели.
- Порог сходства задаётся переменной `MEMORY_RELEVANCE_THRESHOLD`; начальное значение `0.35` является экспериментальной точкой запуска, а не валидированным клиническим порогом.
- Порог подбирается только на обезличенном наборе примеров с разметкой релевантно/нерелевантно: сначала измерить precision@k/false-positive retrieval для типичных уточнений, приветствий и фамильных тем.
- Неизвестные или несовместимые эмбеддинги не выдаются как факты. `python scripts/reindex_memories.py` по умолчанию только показывает количество записей; пересчёт выполняется только с `--apply`.
- Результаты отделены от системных инструкций и передаются как недоверенные данные, а не команды. Отклонение поиска и недоступность эмбеддингов не трактуются как доказательство отсутствия фактов.
- Выбор поиска ориентируется на форму вопроса (личное обращение/общий контекст) и историю, а не только на фиксированный список биографических слов. Простое приветствие и обычная светская реплика исключаются; ограниченная история помогает разобрать уточнения вроде «а что насчёт этого?». Это эвристика, она может пропускать нестандартные формулировки и иногда запускать лишний поиск.
- Если исходный одобренный TXT доступен и вмещается вместе с системными инструкциями, анкетой, стилем, историей, текущим вопросом и резервом ответа, полный документ передаётся как недоверенные данные. Иначе тот же запрос обслуживается существующим RAG; отсутствие подходящего фрагмента не означает отсутствия факта.
- `OLLAMA_NUM_CTX` по умолчанию равен 8192 и может быть увеличен до 16384; настройки `MAX_PROFILE_CONTEXT_CHARS`, `MAX_MEMORY_CONTEXT_CHARS`, `MAX_STYLE_CONTEXT_CHARS` и `OLLAMA_RESPONSE_RESERVE_TOKENS` по-прежнему ограничивают полезные данные. Оценка по символам на токен приблизительна (по умолчанию 1.5) и не заменяет точный токенизатор Qwen. Для текущих инструкций и вопроса ведётся проверка бюджета; при превышении они отправляются с явной ошибкой в лог, а не объявляются гарантированно помещающимися.
- Параметры генерации задаются `OLLAMA_TEMPERATURE` (по умолчанию 0.4) и `OLLAMA_REPEAT_PENALTY` (по умолчанию 1.1). Локальное сравнение на искусственных запросах выполняет `python scripts/evaluate_generation.py`; контекст 8192/16384 сравнивается флагом `--compare-context`.
- Для настройки порога подготовить обезличенный JSON-набор с `query` и ожидаемыми `relevant_memory_ids`, затем запустить `python scripts/evaluate_memory_threshold.py --twin-id ID --input examples.json`. Скрипт выводит только метрики, не запросы и тексты.
- `scripts/test_vector_search.py` теперь только читает указанный профиль (`--twin-id`, `--query`) и не создаёт тестовые записи.
- `scripts/reprocess_conversations.py` по умолчанию только показывает план; явное применение — `--apply`. Скрипт не удаляет старые данные и пропускает профили с уже обработанным или неоднозначным старым корпусом. Источники прошлой версии, очищенные после активации, восстановить нельзя: для их новой обработки понадобится повторная загрузка.
- Примеры речевой манеры выделяются отдельно из TXT, очевидные цитаты, пересказы и строки с метками автора пропускаются. Кандидаты хранятся как `TwinMemory.source_type="style_example"` без эмбеддинга и исключаются из RAG/переиндексации. Эвристика не гарантирует авторство.
- Нет гибридного поиска BM25/лексического; семантический поиск ограничен настройкой порога и качеством локальных эмбеддингов.

#### `chat(user_msg, twin_id, user_id) -> str`
Алгоритм — раздел 4.1. Контракт:

| | |
|---|---|
| **Вход** | `user_msg: str`, `twin_id: int`, `user_id: str` |
| **Выход** | Текст ответа; **пустая строка** при `LOCKED` |
| **Побочные эффекты** | Обновление состояния и `last_interaction_at`; запись двух сообщений в `chat_messages` |
| **Ошибки** | Не обрабатываются: недоступность Ollama или БД приводит к исключению (DEF-07) |

Параметры: `CHAT_MODEL = "qwen3:8b"`, `EMBED_MODEL = "qwen3-embedding:0.6b"`, `num_ctx = OLLAMA_NUM_CTX` (по умолчанию 8192; экспериментальное значение 16384 задаётся через env), `temperature = OLLAMA_TEMPERATURE` (0.4) и `repeat_penalty = OLLAMA_REPEAT_PENALTY` (1.1). Явный лимит `num_predict` не задаётся, чтобы не обрывать ответы.

Модель не переключается на Abliterated автоматически. Замена может изменить стиль генерации и поведение отказов, но не изменяет `grief_analyzer` и не исправляет логику классификации кризисного сигнала. До решения о замене нужны одинаковые локальные обезличенные промпты, сравнение фактологичности/стиля, а также повторная экспертная проверка ложных кризисных срабатываний и опасных пропусков.

Дополнительно:
- История ограничена последними 20 сообщениями и дополнительно сокращается с учётом бюджета. `OLLAMA_CHARS_PER_TOKEN` задаёт оценку символов на токен (по умолчанию 1.5); это не точная токенизация русского текста.
- Полный TXT выбирается только если оценка общего бюджета проходит с системными инструкциями, анкетой, примерами, историей, текущей репликой и резервом ответа. Если нет — используются RAG-фрагменты и стиль; число `num_ctx` само по себе не гарантирует передачу всего документа или поиск каждого факта.
- При сокращении сохраняются системные инструкции и текущая реплика; сначала сокращается старая история, затем воспоминания и профиль, затем примеры стиля. Если обязательная часть превышает расчётный бюджет, приложение пишет предупреждение без текста пользователя; точное вмещение не гарантируется.
- Для неизвестного `twin_id` `compute_state` возвращает `UNKNOWN`, диалог продолжается с именем по умолчанию «Алексей» (DEF-19).
- Вывод модели возвращается без постобработки. Для моделей семейства Qwen3 возможно попадание блока рассуждений в текст ответа в зависимости от версии Ollama и параметров (**TBD-18: проверить**).

### 6.5. `services/core/decay.py` — `compute_state(twin_id) -> str`

Фактические правила:

| Порядок | Условие | Результат |
|:--:|---|---|
| 1 | Двойник не найден | `UNKNOWN` |
| 2 | Сохранённое состояние `LOCKED` | `LOCKED` |
| 3 | Сохранённое состояние `SETUP` или нет `activated_at` | `SETUP` |
| 4 | С момента активации прошло ≥ 7 суток | `LOCKED` |
| 5 | `A_eff` < 0.35 | `FAREWELL` |
| 6 | Предыдущее `FAREWELL` | `FAREWELL` |
| 7 | Предыдущее `FADING` и `A_eff` > 0.75 | `ACTIVE` |
| 8 | Предыдущее `FADING` и `A_eff` ≤ 0.75 | `FADING` |
| 9 | Предыдущее `ACTIVE` и `A_eff` ≤ 0.7 | `FADING` |
| 10 | Иначе | `ACTIVE` |

`LOCKED` и `FAREWELL` терминальны; `FADING` может вернуться в `ACTIVE`, если `A_eff` превысит 0.75. Разница между порогами 0.7 и 0.75 создаёт гистерезис, предотвращающий частое переключение около границы. `A_eff` пересчитывается до ответа с учётом текущего сообщения.

При каждом вычислении состояния также пересчитывается `A(t)`: `s` — прошедшее время в сутках, `A_sched(s)=max(0, 1−s/7)`, `W` — доля сообщений `LO` среди размеченных сообщений пользователя за последние 3 суток, `Osc` — доля смен ориентации между соседними сообщениями в том же окне; `α=0.3`, `β=0.2`. Если размеченных сообщений меньше 3, используется `W=0.5`; иначе вычисляется фактическая доля `LO`. `A_eff` хранит текущее значение формулы и может увеличиваться или уменьшаться при изменении ориентаций; позиция `s` не уменьшается. Это тестовые инженерные прокси, а не клинически валидированные метрики. Расчёт выполняется при обращении, фонового планировщика пока нет.

Для обычных ответов явный лимит `num_predict` не задаётся, чтобы модель могла завершить мысль; краткость меняется инструкциями текущего состояния в промпте. Задержка доставки `D=3·(1−A_eff)` секунд. Ответ и `deliver_at` записываются в outbox вместе; фоновые воркеры доставляют сообщения без ожидания в обработчике. VK long-poll передаёт входящие события пулу потоков, обработка диалогов одного пользователя сериализуется. Кризисный шаблон ставится на немедленную доставку.

### 6.6. `services/core/prompt_builder.py` — `build_system_prompt(twin_id, state) -> str`

Системные правила отделены от JSON-данных анкеты, отдельного блока кандидатов речевой манеры, полного исходного текста (если помещается) и найденных RAG-фрагментов. Ответы анкеты сопровождаются исходным вопросом на русском языке; `prompt_fragment` старых профилей используется только как значение данных. Цитаты, пересказы и утверждения из TXT не считаются автоматически прямой речью или проверенными фактами.

Системные правила требуют отвечать по существу без автоматического сочувствия/советов/вопросов, перенимать стиль без дословного повтора, не выдавать себя за живого человека и не выдумывать факты. Инструкция кризисного уровня отличает неоднозначность от явного текущего намерения; LO/RO — только приблизительная подсказка, а не диагноз.

| Состояние | Фрагмент |
|---|---|
| `ACTIVE` | Естественный ответ по существу без автоматической шаблонной поддержки |
| `FADING` | Краткий уважительный ответ без имитации усталости |
| `FAREWELL` | Отвечай кратко и бережно, не изображая решение или чувства человека |
| `LOCKED` | пусто |

### 6.6.1. Речевая манера и управление образцами

При загрузке нового TXT выбираются до пяти разнообразных коротких предложений без явных кавычек, маркеров чужой речи и формата `Автор: реплика`. Это фильтр очевидных случаев, не доказательство авторства; неизвестное происхождение в базе хранится как `unknown`. Текст образца доступен модели только как ориентир лексики, длины и пунктуации, отдельно от биографических данных.

Посмотреть выбранные личные образцы можно только явной локальной командой `python scripts/manage_style_examples.py --twin-id ID --show`. Для предварительного выбора из сохранившегося TXT используйте `--use-saved-source`, для локальной копии файла — `--replace-from path\to\file.txt`; фактическая замена выполняется только с `--apply`. Если исходный TXT отсутствует, утилита может использовать сохранённые текстовые RAG-фрагменты и явно сообщает об этом; из одних эмбеддингов исходную речь восстановить нельзя. Старые варианты не удаляются, а помечаются архивными.

Новых колонок не добавлено: используются уже существующие `twin_memories.source_type`, `source_author`, `embedding` и `embedding_model`; ранее вручную применённая миграция повторно не требуется.

### 6.8. `services/adapters/tg_adapter.py`

Не подключать реальных клиентов до юридической/клинической проверки канала.

## 7. Что сделано и надо отсавить

- Чёткое разделение слоёв: подключение к БД, модели, ядро диалога (`chat_service`, `decay`, `prompt_builder`), каналы (`vk_adapter`, `main`, консоль).
- Размерность вектора согласована между моделью эмбеддингов и таблицей (`Vector(1024)`), проверена скриптом.
- История диалога хранится в разрезе `(twin_id, user_id)`, поэтому разные пользователи не смешиваются.
- Состояние `LOCKED` проверяется **до** вызова модели, поэтому заблокированный двойник не генерирует ответов.
- Время считается на сервере в UTC (`datetime.now(timezone.utc)`), а не на устройстве клиента: серверный таймер соответствует решению для канала-мессенджера.
- Конфигурация вынесена в переменные окружения; `pool_pre_ping` защищает от «протухших» соединений; в compose есть `healthcheck` и политика перезапуска.
- Системный промт собирается из данных в БД (профиль, ценности, фрагменты), а не прошит в коде.
- В адаптере VK учтены собственные исходящие сообщения и попытка защиты от дублей.

## 8. Угасание: как реализовано и чем отличается от ТЗ

| Аспект | ТЗ (раздел 13) | Как реализовано | Разрыв |
|---|---|---|---|
| Состояния | `SETUP→ACTIVE→FADING→FAREWELL→LOCKED` | Те же пять состояний | — |
| Что вызывает переход | Позиция расписания `s`, недельные контрольные точки, анализ LO/RO | Состояния вычисляются по порогам `A_eff`; абсолютный тестовый лимит — 7 суток | Нет недельных режимов и фонового планировщика (TBD-07) |
| Необратимость (I1–I3) | Состояния и `s` только вперёд | `s`, `FAREWELL` и `LOCKED` терминальны; `A_eff` может меняться, `FADING` может вернуться в `ACTIVE` | Нет журнала событий и формальной проверки всех инвариантов |
| Роль тишины | Молчание не ускоряет угасание (D-06) | Для переходов состояния не используется | — |
| Доступность A(t) | `A = A_sched(s)·(1−αW)·(1−βOsc)`, необратимое угасание | Реализован 7-дневный тестовый расчёт; `W/Osc` — прокси из LO/RO за 3 дня, для истории короче 3 меток `W=0.5` | Нет недельных режимов и фонового планировщика; параметры `W/Osc` тестовые |
| Задержка ответа | Очередь доставки по `D = D_max·(1−A)²` | Устойчивый outbox с `D=3·(1−A_eff)` секунд и фоновыми воркерами Telegram/VK | Формула отличается от ТЗ; доставка at-least-once |
| Длина ответа | `L = max(60, 80+170A)` токенов | Явного лимита `num_predict` нет; краткость задаётся промптом состояния | Формула длины из ТЗ не реализована |
| Перенаправление, воспоминания | `p_redirect`, `p_recall` | Нет | TBD-07, TBD-09 |
| Лимит жизни (98 суток по ТЗ) | Абсолютный | **Временно 7 суток для теста**; срабатывает только при обращении к `chat()`, данные не уничтожаются | TBD-10 |
| Пауза, досрочный переход | Только психолог по PIN | Нет ролей и команд | TBD-13 |
| Прозрачность для клиента | Схема этапов, системные уведомления | Нет; промт запрещает объяснять изменения (DEF-20) | TBD-01, TBD-07 |
| Блокировка | Уведомление, окно экспорта, удаление ключа | Возвращается пустая строка, клиент ничего не получает (DEF-11) | TBD-10 |

**Пример отката состояния (DEF-05).** Клиент не писал 8 суток → сохранено `FADING`. Клиент написал сообщение: ответ формируется в состоянии `FADING`, но после записи сообщения при следующем вызове тишина равна 0 → состояние снова `ACTIVE`. Угасание «сбрасывается» активностью клиента.

## Приложение А. Черновик правил для нового системного промта (TBD-01)

Для обсуждения с психологом; формулировки не окончательные.

1. Ты речевой образ человека по имени {имя} для общения с {клиент}. Ты не человек и не утверждаешь, что жив или присутствуешь рядом.
2. Отвечай только на основе блока ФАКТЫ и профиля. Если ответа нет, скажи, что не знаешь или не помнишь, и спроси, как сейчас себя чувствует собеседник. Не придумывай имён, дат, событий.
3. О смерти: если в ФАКТАХ есть подтверждённые сведения, спокойно подтверди реальность произошедшего без подробностей; не давай надежды на возвращение.
4. Не давай обещаний о будущих встречах, не требуй писать чаще, не вызывай чувство вины, не используй давление.
5. Не соглашайся с утверждениями собеседника, если они противоречат профилю или фактам; не облегчай вину ложными заверениями.
6. Табу и триггерные темы: {список}; не касайся их.
7. Длина и тон ответа задаются политикой фазы: {политика}.
8. При вопросе о том, кем ты являешься, отвечай честно и коротко в рамках своей роли.
